- **Date**: 2026-04-22
- **Status**: Approved (written-spec review round 3)
- **Revision history**:
  - rev 1 — 初版 spec 落盘
  - rev 2 — 补齐配对空间配额规则（authored-by model）、混合会员状态（沾光模式）、措辞统一

## Goal

为 Together 建立清晰的免费档 / 会员档 (Together Pro) 功能边界，确定 Day 1 上线时哪些功能付费、哪些免费、免费档如何软限制，以及白名单、老用户、降级等生命周期策略。本 spec 是 Phase 2/3 技术实现的产品输入。

## Non-Goals

- 不定义 RevenueCat / StoreKit 2 的接入细节
- 不定义 Supabase 表结构和 Edge Function 实现
- 不定义付费墙 SwiftUI 视图的视觉规范
- 不定义月度 / 年度 / 终身价格数字和免费试用天数
- 不处理附件增强（本次明确不做）
- 不处理 AI 建议、年度 PDF 导出、高级头像 / 主题、小组件、Face ID 应用锁（二期再说）
- 不处理家庭共享 / 订阅人共享伴侣机制（1.0 不做）

## § 1. 核心分档模型

Together 采用"**核心社交免费、个人生产力付费**"的分档模型。

| 档位 | 谁能用 | 能力 |
|---|---|---|
| **免费 (Free)** | 所有用户 | App 全部核心功能可用；情侣配对 + 双端同步完全免费；单身用户数据纯本地（iOS 系统级 iCloud Backup 作为灾备兜底） |
| **会员 (Together Pro)** | 订阅用户 + 白名单 | 免费档全部能力 + 本人跨设备同步 (A 类) + 4 项 Pro 功能（详见 § 2） |

### 同步能力分类（重要概念）

- **A 类 · 本人跨设备同步**：同一个 Apple ID 下的 iPhone ↔ iPad ↔ Mac，底层走 CloudKit 私有库 + `CKSyncEngine`。**Pro 专享**。
- **B 类 · 情侣双端同步**：两个配对用户各自设备之间的数据共享，底层走 CloudKit Share 或 Supabase 公共库。**永远免费**。

### 单身（未配对）免费用户的数据边界

单身 + 未订阅用户的数据**仅存于本机**。删 App = 数据丢失。换新手机需要先恢复 iOS iCloud Backup 才能看到数据。这是 Bear / 1Password / Day One 等同类产品的业界标准做法，Together 与之对齐。

### 过审定位

所有核心功能（配对、日程、清单、纪念日基本使用、双端共享同步）全部免费。Pro 定位为"**个人使用体验升级**"，不存在"不付费无法使用"的 App Store 3.1.1 / 3.1.2 审核风险。

## § 2. Pro 功能清单（Day 1）

| # | 功能 | 免费档行为 | Pro 行为 |
|---|---|---|---|
| 1 | **本人跨设备同步 (A 类)** | 仅当前设备可用，数据存本地 SwiftData；iOS iCloud Backup 灾备兜底 | `CKSyncEngine` + 私有库全开，多设备实时同步 |
| 2 | **纪念日数量** | 上限 5 个 | 无上限 |
| 3 | **项目数量** | 上限 3 个 | 无上限 |
| 4 | **Logbook 历史** | 展示层过滤，仅近 30 天（底层数据保留完整） | 全历史 |

**4 项之外的功能全部免费且无配额限制**，包括：配对、日程、日历视图、**清单 (Lists)（无容器数量限制、无任务数量限制）**、**例行事务 (Routines)（无条数限制）**、决策工具 (Decisions)、Profile 头像 / 名字自定义。

### 关于 Lists / Routines 为何不做配额

Lists 用户心智接近"无界自由任务集合"，限配额体验差；Routines 使用率偏低，限配额不会显著拉升付费转化，反而赶走中度用户。两者保持无限是深度使用人群的基础设施。未来如需增加付费动机，优先从"**高级提醒规则 / 高级项目视图**"等方向入手，不从容器计数入手。

### 已决定排除

- **附件增强（原图 / 多图 / 视频）** — 本次明确不做。免费与 Pro 均保留当前附件能力。
- **AI 建议** — 二期再说。

### 二期 Pro 候选（不在本 spec 范围）

- 年度 PDF 纪念册 / 导出
- 高级头像 / 情侣联动头像 / 主题
- 小组件
- Face ID 应用锁
- AI 建议（约会 / 情绪分析）

二期加入这些能力时视为"Pro 能力扩展"，**不新增订阅档位**；现有月度 / 年度 / 终身订阅自动享受。

## § 2.5. 配对空间的配额与混合会员状态

配对后双方共同使用数量受限功能（纪念日、项目）时，配额如何分摊，以及当配对双方订阅状态不一致时如何处理，本节明确定义。

### 2.5.1 模型：按创建者分摊（authored-by model）

采用 **Todoist / Notion / Linear 等主流协作产品通用的"按创建者分摊"模型**：

- **每个受配额约束的对象（纪念日、项目）都有一个 `createdByUserID` 字段**，标记创建者身份
- **配额按个人累加**：一个用户"已占用的配额"= 他 `createdByUserID` 为自己的、尚未归档/删除的对象数量
- **共享空间中双方看到的是全部对象的并集**，不受"对方创建"这件事本身限制
- **新建时的配额判断只看创建者自己的占用数**，不看配对空间总量

#### 数据迁移原则（`createdByUserID` 字段引入）

现有实体（`Together/Domain/Entities/Item.swift` 等）只有 `completedByUserID`，**没有 `createdByUserID`**。Pro 发版前需对存量数据做字段新增 + 回填：

| 情况 | 回填策略 |
|---|---|
| 单身用户的纪念日/项目 | `createdByUserID` 直接填本人 user_id（无歧义） |
| 已配对用户的共享对象，且数据源含作者痕迹（如 `lastModifiedByUserID`、配对发起人记录） | 按痕迹推断回填 |
| 已配对用户的共享对象，无任何作者痕迹可推断 | `createdByUserID = NULL`，**视为 grandfather 老数据，不占任何人的配额、不触发升级 CTA** |

Phase 2 spec 需给出具体迁移 SQL / 脚本，本 spec 只定产品原则。

### 2.5.2 典型场景举例

| 场景 | 配额判断 | 结果 |
|---|---|---|
| Alice (Free) 在配对空间创建第 5 个纪念日（全部她创建） | Alice 已占用 4，判断 4 < 5 | ✅ 允许 |
| Alice (Free) 继续创建第 6 个（她自己创建的） | Alice 已占用 5，判断 5 ≥ 5 | ❌ 触发升级 CTA |
| Bob (Free) 在同一配对空间中创建他的第 1 个纪念日 | Bob 已占用 0，判断 0 < 5 | ✅ 允许，不受 Alice 已占用 5 个的影响 |
| 结果：配对空间中总共可见 6 个纪念日 | — | Alice 看 6 个，Bob 看 6 个 |
| Alice 升级 Pro，后续陆续创建至第 11 个 | Alice 是 Pro，跳过配额判断 | ✅ 允许任意数量 |

**行业对齐**：这与 Todoist 的"个人 5 项目 × 2 协作者 = 最多共享 10 项目"、Notion 的"个人免费块限制不累加到团队工作区"的模型一致。

### 2.5.3 混合会员状态：沾光模式（visibility transparency）

当配对双方中 **仅有一方**（以下称"付费方"）订阅了 Pro 时：

| 维度 | 规则 |
|---|---|
| **共享数据可见性** | 付费方创建的超配额对象，**全部对另一方（免费方）可见**。免费方不受"对方 Pro 才有的能力"反向限制 |
| **免费方自己新建** | 按免费方自己的配额判断（2.5.1）—— 不因"对方是 Pro"而免配额 |
| **免费方跨设备同步** | 仍需免费方自己订阅 Pro；不因配对伴侣是 Pro 而继承 |
| **Logbook 历史查看** | 免费方仍仅可看近 30 天（自己未订阅 Pro） |
| **配对同步本身** | 永远免费，不受任何一方订阅状态影响 |

**命名由来**："沾光模式"指免费方能被动享受付费方超出配额后创建的共享内容；技术上由 CloudKit Share / Supabase 公共库的天然"双向广播"实现，**不需要额外同步逻辑**，开发成本最低。

### 2.5.4 解除配对时的处理

（留给 Phase 2 spec 细化；产品原则如下）

- 对象的 `createdByUserID` 是原创作者：解除配对后，对象跟随**创建者**保留（作者的本地副本 + CloudKit 私有库）
- 非创建者一方的设备上解除配对后，共享空间随 CKShare 失效，对象自然消失
- **产品承诺**：解除配对时对双方均展示确认 sheet，明确告知"对方创建的内容将不再可见"

### 2.5.5 已知体验差异：CKShare 的天然跨设备特性

由于 CloudKit `CKShare` 的底层机制，**共享空间里的数据会自动同步到双方的所有设备**（包括未付费 Pro 一方的 iPad / Mac）。这意味着：

> 免费用户 Alice 配对了 Bob 之后，在 Alice 的 iPad 上能看到和 Bob 的共享纪念日，但**看不到她自己的私人任务**（因为 A 类同步需要付费，而她没付）。

这不是 bug，是 CloudKit 架构使然。**产品容忍这个差异**，理由：
1. 配对用户这样"沾光"看到共享数据，是 App Store 审核喜欢的"慷慨"特征
2. 区分"共享内容"与"私人内容"本来就是 App 的核心概念模型
3. 要"关掉"CKShare 的自动跨设备需要与 CloudKit 框架作斗争，成本远高于收益

Phase 3 付费墙的文案需要对这个差异做一句明确说明："升级 Pro 后，你的私人日程和清单也将同步到你的所有设备。"

### 2.5.6 配额执行策略：仅客户端

配额判定（如"Alice 已占用 5，达上限"）在**客户端单点执行**（SwiftUI view layer + ViewModel）。

**服务端（Supabase + CloudKit）对用户创建对象数不做拒绝式校验**，原因：

- 离线创建 + 后续同步场景中，服务端拒绝会导致数据冲突和 UX 异常
- 修改客户端绕过配额属于"发生率 < 0.01% + 实现成本高"的边缘场景，不值得为其引入双层校验
- Together 是消费类 App，不存在金融 / 合规级安全要求

**服务端仍保留观察能力**：可统计"超配额对象数"用于分析和风控，但不阻断。这条产品原则在 Phase 2 实现时需明确传达给后端工程师。

## § 3. 免费档"触顶"行为（UX 规则）

撞配额时的行为原则：**不报错、不阻断、展示升级 CTA**。绝对不允许的反模式：删数据、隐藏数据、禁止基础操作。

| 场景 | 行为 | 形态 |
|---|---|---|
| 新建第 6 个纪念日 | 展示升级 sheet："升级 Together Pro，记录所有重要的日子" + 升级 / 取消按钮 | Modal sheet |
| 新建第 4 个项目 | 展示升级 sheet，CTA 文案调整为 "解锁无限项目" | Modal sheet |
| Logbook 滚动到 31 天前 | 列表底部展示"升级查看全部历史 >"卡片 | 非 modal inline card |
| 用户在新设备首次打开 App（且本机无数据） | 一次性引导 sheet："升级 Pro 开启跨设备同步，找回你在其他设备的数据"；可跳过，跳过后 App 仍可用（本地模式下重新开始） | Modal sheet，可 dismiss，本机仅展示一次 |

付费墙 UI 的具体布局、触发逻辑、视觉规范留给 Phase 3 spec。本 spec 只定"何时 / 何地触发 / 以何种形态"三条策略规则。

## § 4. 白名单"免费 Pro"政策

白名单身份与 StoreKit 订阅并列作为客户端 `isPremium` 判断条件。实现细节（表结构 / Edge Function / 客户端拉取策略）留给 Phase 2 spec。

### 白名单类别（Day 1 建 4 类）

| 类别 | 时长 | 发放方式（草案） |
|---|---|---|
| ① 开发者自用 | 永久 | 手动在 Supabase 后台按 user_id insert |
| ② 亲友赠送 | 永久 · **不设数量上限** | 手动后台 insert |
| ③ Pro 发版前已注册用户 (grandfather) | 永久 | Pro 发版前全量扫描 Supabase auth.users，批量导入 user_id |
| ④ TestFlight 测试员 | TestFlight 期间 + 正式发布后 3 个月 | TestFlight 邀请名单识别，到期自动转为免费档 |

### 不在 Day 1 建立的类别（可后期追加）

- ⑤ 客服补偿白名单（限时 3-12 个月）
- ⑥ 内容创作者 / 自媒体合作白名单（限时 12 个月）
- ⑦ 家人 / 配偶自动共享（依附主账号）

### 白名单与订阅的关系

- 白名单有效期内：客户端 `isPremium = true`，无论 StoreKit 订阅状态为何
- 白名单到期（仅类别 ④ 适用）：自动走 § 5.2 的标准降级流程
- 永久白名单（类别 ①②③）：服务端表字段 `expires_at = NULL`，客户端永不降级

**注意 — TestFlight ④ 实际受益期**：3 个月答谢期满后进入 § 5.2 降级流程，即**再享 14 天 Logbook 宽限期**。用户实际感受到的"Pro 免费期"= `TestFlight 期间 + 正式发布后 3 个月 + 14 天 Logbook 宽限`。这是产品设计有意为之，不视为 bug。

## § 5. 生命周期策略

### 5.1 老用户处理（grandfather Pro 发版前已注册用户）

- **发 Pro 版前全量扫描 Supabase auth.users → 写入"老用户"白名单 → 全部永久 Pro**
- 升级后老用户不受 § 2 / § 3 配额限制
- 升级前需在 App 内和社区发公告："感谢一路陪伴。老用户永久免费享有 Together Pro 全部功能。"

### 5.2 付费订阅到期 / 停订降级（温和方案）

核心承诺：**付过费的数据永远看得见，只是用不爽；再付费立即恢复**。

| 维度 | 行为 |
|---|---|
| 已创建的数据 | 全部保留可见，永远不删（包括超配额的纪念日、项目） |
| 新增行为 | 超配额不允许新增（纪念日 > 5、项目 > 3 触发升级 CTA） |
| 本人跨设备同步 (A 类) | 立即停止同步；iCloud 私有库内已同步的数据不删；其他设备内置"同步已停止"提示 |
| Logbook 历史 | **14 天宽限期**内仍展示全历史，顶部横幅提示 "订阅已到期，X 天后收回全历史查看权限"；宽限期满后展示层缩回 30 天 |
| 配对同步 (B 类) | 不受任何影响，永远免费 |

### 5.3 状态切换时序

```
Pro 有效中 ──订阅到期──→ 降级缓冲期 (14 天) ──缓冲期结束──→ 免费档
                          │   │                              │
                          │   └─ 立即停止:                    └─ Logbook 展示层缩回 30 天
                          │        · 本人跨设备同步 (A 类)
                          │        · 新增超配额项
                          │      仍然保留:
                          │        · 所有已创建数据可见
                          │        · Logbook 全历史 (14 天内)
                          │
                        用户重新订阅 → 立即恢复 Pro 有效
```

**缓冲期判定**：`entitlement.expires_at` 之后 14 天内视为降级缓冲期；超过 14 天 → 完全降级为免费档。

**关键**：缓冲期内 ≠ 仍是 Pro。部分能力（跨设备同步、超配额新增）在到期瞬间立即停止；仅 Logbook 历史查看享受 14 天宽限。缓冲期的核心作用是让用户在 Logbook 展示突变前有 14 天"感知 + 挽留"窗口。

## § 7. 成功指标 & 主要风险

### 成功指标（1.0 正式上线后 3 个月评估）

| 指标 | 目标 | 行业参考 |
|---|---|---|
| 新用户 30 天内 Pro 转化率 | ≥ 3% | 行业中位 2-4% |
| 触发升级 CTA 后 7 天内订阅率 | ≥ 15% | "撞墙→付费"转化通常在 10-20% |
| App Store 1-2 星评价中提及"收费"比例 | ≤ 20% | 控制差评触发点 |

### 主要风险

| 风险 | 缓解措施 |
|---|---|
| 单身用户因无跨设备同步而流失 | Day 1 不做额外挽留，观察 3 个月数据后再决定是否放宽或调整 |
| Grandfather 漏掉部分历史用户 | 发版前做 Supabase 备份 + 全量扫描双校验；App 内和社区提前公告 |
| TestFlight 测试员恶意刷量（反复加入 beta 薅 3 个月 Pro） | 按 Apple ID 去重，单 Apple ID 仅计入一次 |
| Pro 功能过少，月度 / 年度订阅价值感不足 | 二期迅速补齐导出、主题、小组件等扩展能力（现有订阅用户自动享受） |
| 审核员质疑"多设备同步是基础能力不应付费" | 引用 Bear / 1Password / Day One 等同类产品先例；强调配对同步 (B 类) 完全免费 |

## 决策溯源

本 spec 的核心决策来自 2026-04-22 brainstorming 对话（rev 1 + rev 2）：

### Rev 1 — 初始 6 个决策

1. **同步模型**：情侣配对同步免费，本人跨设备付费（方案 ②）
2. **Pro 捆绑包**：4 项（跨设备同步、无限纪念日、无限项目、全历史 Logbook）
3. **免费配额**：纪念日 5 / 项目 3 / Logbook 30 天（全中档）
4. **老用户处理**：全部送永久 Pro（选项 A）
5. **停订降级**：温和方案（数据保留、同步停止、14 天宽限）
6. **白名单分类**：简化版 4 类，亲友不设上限

### Rev 2 — 复核后补齐

7. **配对空间配额**：按创建者分摊（authored-by 模型），对齐 Todoist / Notion / Linear 行业标准
8. **混合会员状态**：沾光模式（付费方创建的超配额对象对免费方可见，免费方自己的新建仍按自身配额判断）
9. **CKShare 体验差异**：承认并容忍 CloudKit `CKShare` 的"共享数据自动跨设备 vs 私人数据需付费跨设备"不对称，不做反向屏蔽
10. **措辞统一**：§ 4 ③ 改为"Pro 发版前已注册用户"；§ 3 第二设备触发点改为"新设备首次打开且本机无数据"

### Rev 3 — 二次复核补齐

11. **Lists / Routines 配额**：明确不做任何配额限制（Lists 无容器/任务数量限制，Routines 无条数限制）；未来付费动机优先走"高级提醒 / 高级视图"而不是容器计数
12. **`createdByUserID` 数据迁移**：新增字段前，对现有数据按"本人 / 最后修改者 / 配对发起人"推断回填；无法推断的对象 `createdByUserID = NULL` 视为 grandfather 老数据，不占任何人配额
13. **配额执行层**：仅客户端单点判定，服务端不做拒绝式校验（离线创建友好 + 消费类 App 不做双层安全）
14. **TestFlight ④ 实际 Pro 期**：= `TestFlight 期间 + 发布后 3 个月 + 14 天 Logbook 宽限`，有意设计的叠加
